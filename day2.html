Day 2

技术讨论与提问 Tech Discussion

描述 bug、澄清需求、确认理解。会提问的工程师，比只会闷头做的工程师走得更快。

今日目标

  1. 能用英文把一个 bug 的现象、复现步骤和影响范围讲清楚。
  2. 掌握澄清需求（clarifying questions）的 6 种问法，避免做错方向。
  3. 会用 "Just to make sure we're on the same page" 类句型做理解确认。

核心句型

① 描述 Bug / 问题

I'm running into an issue with the checkout flow — the page freezes after I click "Pay".
结账流程有个问题——点「支付」之后页面就卡死了。
遇到问题 · run into an issue
I can reproduce it consistently on Chrome, but not on Safari.
在 Chrome 上每次都能复现，Safari 上不行。
复现 · reproduce consistently
It happens intermittently — maybe one in five times.
它是偶发的——大概五次里出现一次。
偶发 · intermittent
The error message says "connection timed out", but the network looks fine.
报错信息是「连接超时」，但网络看起来正常。
引用报错信息
It only affects users on the legacy version, so the impact is limited.
只影响旧版本用户，所以影响范围有限。
影响范围 · impact

② 澄清需求（Clarifying Questions）

Just to clarify — do you mean we should support both formats, or just the new one?
确认一下——你的意思是两种格式都要支持，还是只支持新的？
二选一确认 · Just to clarify
Could you walk me through the expected behavior step by step?
你能一步步给我讲讲期望的行为吗？
请对方演示 · walk me through
What should happen if the user loses connection midway?
如果用户中途断网，应该怎么处理？
边界情况 · edge case
When you say "fast", what kind of latency are we targeting?
你说「快」，我们的目标延迟是多少？
量化模糊需求 · 典型工程师问法
Is this a must-have for the launch, or can it wait until the next release?
这是上线的硬性要求，还是可以等下个版本？
优先级 · must-have vs nice-to-have

③ 确认理解（Confirming Understanding）

So if I understand correctly, we need to migrate the data before the schema change. Is that right?
所以我理解得对的话，我们需要在改表结构之前迁移数据，对吗？
复述确认 · If I understand correctly
Just to make sure we're on the same page — the deadline is the 15th, not the 20th?
确认下我们理解一致——截止日期是 15 号，不是 20 号吧？
on the same page 最常用
Let me play that back to you to make sure I got it right.
我复述一遍，确认我没理解错。
play back = 复述
Does that make sense, or should I explain it differently?
这样讲清楚吗？还是我换个方式解释？
讲完后确认对方理解

情景对话

场景一：向资深同事求助一个 bug（详细描述问题）

你Hey Sarah, do you have a minute? I'm running into a weird issue with the export feature, and I've been staring at it for two hours.Sarah，有空吗？导出功能有个奇怪的问题，我盯着看了两个小时了。
SarahSure, what's going on?可以，什么情况？
你So when a user exports a report larger than 10,000 rows, the request times out after 30 seconds. Small reports work fine. I can reproduce it consistently in staging, but the logs don't show any exceptions — the process just gets killed.就是当用户导出超过一万行的报表时，请求 30 秒后超时。小报表没问题。测试环境每次都能复现，但日志里没有任何异常——进程直接被杀掉了。
SarahHmm, no exceptions but the process dies... That sounds like the gateway timeout rather than an app issue. What's the gateway timeout configured to?嗯，没有异常但进程挂了……听起来像网关超时，不是应用的问题。网关超时配的多少？
你Good point — I haven't checked that. Let me look... you're right, it's set to 30 seconds. So the fix would be either to increase the timeout or make the export async?有道理——我还没查这个。我看一下……你是对的，配的是 30 秒。那修复方案要么调大超时时间，要么把导出改成异步？
SarahIncreasing the timeout is a band-aid. For reports that big, async with a notification when it's done is the cleaner approach. But that's a product decision too — worth checking with your PM.调超时只是权宜之计。这么大的报表，做成异步、完成后发通知更干净。不过这也是产品决策——值得和你的 PM 确认一下。
你That makes sense. So if I understand correctly, the short-term fix is bumping the timeout, and the long-term fix is moving to an async job. I'll confirm the priority with the PM today.有道理。那我理解对的话，短期方案是调大超时，长期方案是改成异步任务。我今天和 PM 确认优先级。
SarahExactly. Nice job narrowing it down, by the way.完全正确。顺便说一句，你能定位到这一步做得很不错。

场景二：和产品经理澄清一个模糊的需求

PMFor the new dashboard, we want the page to load fast. Users are complaining about the current one.新仪表盘希望页面加载快。用户对现在这个抱怨很多。
你Sure. When you say "fast", what kind of target are we aiming for? For example, first load under two seconds?好的。你说「快」，具体目标是什么？比如首次加载两秒以内？
PMTwo to three seconds sounds right. Oh, and we also want real-time data on it.两到三秒差不多。哦对了，上面还要展示实时数据。
你Just to clarify — "real-time" meaning updates every few seconds, or truly live streaming? That changes the architecture quite a bit.确认一下——「实时」是指每隔几秒刷新，还是真正的实时流？这对架构影响很大。
PMEvery minute would probably be fine. Nothing that fancy.每分钟刷新一次应该就够了，不用那么复杂。
你OK, that's much more doable. What about historical data — how far back do we need to go?好，那就可行多了。那历史数据呢——需要追溯到多久以前？
PMThe last 30 days should cover it.最近 30 天就够了。
你Great. Let me play that back to you: a dashboard loading within 3 seconds, refreshing every minute, with 30 days of history. Is that right?好。我复述一下：一个 3 秒内加载、每分钟刷新、包含 30 天历史的仪表盘。对吗？
PMExactly. Glad we talked this through.完全正确。很高兴我们把这事聊透了。

场景三：技术方案讨论中提出疑问

KevinI propose we use a message queue between the order service and the notification service. It'll decouple them nicely.我建议在订单服务和通知服务之间加一个消息队列，可以把两者很好地解耦。
你Sounds good in principle. One thing I'm not clear on — what happens if the queue is down? Do orders still go through?原则上没问题。有一点我不太清楚——如果队列挂了怎么办？订单还能正常下单吗？
KevinGood question. Yes, the order flow doesn't depend on the queue. Notifications would just be delayed until it recovers.问得好。是的，下单流程不依赖队列。通知只是延迟，等队列恢复再发。
你OK. And what about duplicate messages? If a notification gets delivered twice, that's a bad user experience.好。那重复消息呢？如果通知发两次，用户体验会很差。
KevinWe'd handle that with idempotency keys on the consumer side.我们会在消费端用幂等键来处理。
你Makes sense. I'm on board then — the design looks solid to me.有道理。那我同意了——我觉得这个设计挺稳的。

发音与连读提示

1. "What's going on?" 的口语读法：what's going on 三个词连成一串 /wʌts ɡoʊɪn ɑn/，going 的 g 不用发得很重。

2. "sort of / kind of" 弱化：口语中说 "It's kind of weird" 时，kind of 读作 /kaɪndə/（kinda），表示「有点儿」。

3. 疑问句语调：一般疑问句（Is that right? / Does that make sense?）句尾升调；特殊疑问句（What happens if...?）句尾降调。

练习任务

  • 跟读：三个对话逐句跟读，重点模仿提问句的语调。
  • Bug 描述练习：拿你最近遇到的一个真实 bug，用「现象 → 复现步骤 → 报错信息 → 影响范围」四段结构说出 60 秒的描述，录音。
  • 澄清练习：回想一个你最近接收到的模糊需求，用今天的句型设计 3 个澄清问题并说出来。
  • 复述练习：读完场景二后，不看原文，向空气「复述」需求内容，用 "Let me play that back..." 开头。
