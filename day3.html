Day 3

代码评审 Code Review

Code review 是英语 + 技术 + 沟通技巧的三重考验。今天练两件事：礼貌地给别人提意见，以及得体地回应别人的意见。

今日目标

  1. 会用委婉语气（softening）给同事提代码意见，避免显得指责。
  2. 能区分并表达「必须改」和「建议改」两种不同强度的反馈。
  3. 被评审时能接受意见、解释设计、礼貌坚持自己的方案。

核心句型

① 提意见（给别人评审）

Nice work overall! Just a couple of minor suggestions.
整体做得很棒！只有几个小建议。
开头肯定 · 缓冲句
Nit: this variable name could be more descriptive — maybe "activeUsers" instead of "data"?
小问题：这个变量名可以更有描述性——用 "activeUsers" 代替 "data" 怎么样？
nit = 吹毛求疵的小点，不阻塞合并
Might it be cleaner to extract this logic into a separate function?
把这段逻辑抽成独立函数会不会更清晰？
委婉建议 · Might it be...?
I wonder if we could reuse the existing utility here instead of writing a new one.
我在想这里能不能复用现有的工具函数，而不是新写一个。
I wonder if 极其委婉
This is a must-fix: the query runs inside the loop, so it'll be O(n²) with large datasets.
这个必须改：查询写在循环里，大数据量下会是 O(n²) 的复杂度。
必须改 · must-fix，说清理由
Could you add a test case for the empty-input scenario?
能给空输入的场景加个测试用例吗？
请求补充 · Could you...?
Non-blocking, but for future reference, we usually prefer const over let here.
不阻塞合并，不过供以后参考：这里我们一般用 const 而不是 let。
团队规范但不强制

② 回应反馈（被别人评审）

Good catch! I'll fix that right away.
发现得好！我马上改。
接受意见 · Good catch 最高频
That's fair. Done — pushed the fix.
有道理。改好了——已推送。
简洁接受并完成
I did consider that, but went with this approach because it keeps the API backward-compatible.
我考虑过那个方案，但选了这个，因为它能保持 API 向后兼容。
解释设计权衡
Hmm, I see your point, but I'd slightly prefer to keep it as is — here's why...
嗯，我理解你的意思，但我更倾向于保持现状——原因如下……
礼貌坚持己见
Happy to be convinced otherwise — want to hop on a quick call to discuss?
我很乐意被说服——要不要快速通个电话讨论一下？
意见僵持时转语音，别在线上拉锯
Thanks for the thorough review! Addressed all comments — could you take another look?
感谢这么仔细的评审！所有意见都处理了——能再看一眼吗？
改完请求复审 · re-review

情景对话

场景一：你评审同事的 PR（当面友好交流）

你Hey Mark, I left some comments on your PR — overall it looks great, just a couple of things worth discussing.Mark，我在你的 PR 上留了些评论——整体很不错，有几个点值得聊聊。
MarkSure, what did you have in mind?好，你觉得哪些地方？
你The main one is the user lookup — it's inside the loop, so we'd hit the database once per item. With a batch of a thousand orders, that's a thousand queries. Could we batch-load the users up front?主要的是用户查询——它写在循环里，每条数据都会查一次数据库。一千个订单就是一千次查询。能不能提前批量加载用户？
MarkAh, good point. I didn't think about the volume. Yeah, I can pre-fetch them with a single query using an IN clause.啊，有道理。我没考虑到数据量。可以用 IN 子句一次查出来。
你That'd be perfect. The other ones are just nits — a couple of naming suggestions and a missing test for the error path. Nothing blocking.那就完美了。其他都是小问题——几个命名建议和错误分支缺个测试。都不阻塞合并。
MarkGot it. I'll address them this afternoon and ping you for a re-review.明白。我下午处理完再喊你复审。
你Sounds good. Thanks for moving fast on this!好的。谢谢你推进得这么快！

场景二：你的 PR 被评审，礼貌坚持自己的方案

SarahI left a comment on the caching layer — I think a Redis cache would be better than the in-memory one you wrote.我在缓存层留了条评论——我觉得用 Redis 缓存比你写的内存缓存更好。
你Thanks for taking a look! I did consider Redis, but for this feature the data is per-user and tiny — a few KB at most. An in-memory cache avoids a network hop and keeps the deployment simple.谢谢你来看！Redis 我考虑过，但这个功能的数据是按用户隔离的，而且很小——最多几 KB。内存缓存能省一次网络请求，部署也简单。
SarahFair enough, but what happens when we scale to multiple instances? Each pod would have its own cache.有道理，但扩到多实例怎么办？每个 pod 各有一份缓存。
你That's the one scenario where Redis wins. If multi-instance is on the roadmap for this quarter, I'm happy to switch to Redis now. Do you know what the plan is?那是 Redis 更优的唯一场景。如果多实例在这季度的规划里，我现在就乐意换成 Redis。你知道计划吗？
SarahMulti-instance is coming next month, actually.多实例下个月就要上了。
你Then let's do it your way — better to pay the cost once now than refactor again next month. Good catch.那就按你说的办——现在付一次成本，好过下个月再重构。发现得好。
SarahAppreciate you being open about it. That's a solid PR otherwise.感谢你这么开放地讨论。这个 PR 其他方面很扎实。

场景三：评审中的分歧升级处理（文字拉锯转语音）

Kevin(comment) I still think we should handle the retry logic in the service layer, not the client. Two rounds of comments on this already.（评论）我还是觉得重试逻辑应该放在服务层，而不是客户端。这个已经来回两轮评论了。
你I think we're going back and forth on this one. Happy to be convinced otherwise — do you have 10 minutes for a quick call? Might be faster than more comments.我觉得这点上我们在来回拉锯。我很乐意被说服——有 10 分钟通个电话吗？可能比继续留言快。
KevinSure, calling you now.可以，现在打给你。
你...OK, so on the call we agreed: retries stay on the client for now, and Kevin will file a follow-up ticket to centralize retry logic in the service layer next sprint. I'll note that in the PR.……好，电话里我们达成一致：重试暂时留在客户端，Kevin 会开一张后续工单，下个迭代把重试逻辑统一收敛到服务层。我把这个记在 PR 里。
KevinWorks for me. LGTM once that comment is added.我没问题。评论加上后我就 LGTM（看起来不错，同意合并）。

发音与连读提示

1. "Good catch" 的 catch：/kætʃ/，注意和 "cache"（/kæʃ/，缓存）区分——技术会议上这两个词经常同时出现！

2. "a couple of" 弱读：口语中读作 "a coupla" /ə ˈkʌplə/，"a couple of things" 是委婉提意见的经典开场。

3. LGTM / nit / PR 缩略语：会议上直接读字母（L-G-T-M）或单词（nit /pr/），平时听力多留意。

练习任务

  • 跟读：重点练三个对话中的委婉句型，注意 "Might it be..." "I wonder if..." 的柔和语调。
  • 强度分级练习：对同一个问题（如「变量命名不好」），分别用 nit / 建议 / must-fix 三种强度各说一遍，感受语气差异。
  • 反驳练习：设想别人批评你的方案，用「感谢 + 解释理由 + 抛出条件」结构说出你的回应。
  • 实战：今天找一条真实的 PR 评论（自己的或别人的），试着用英文口头表达一遍。
